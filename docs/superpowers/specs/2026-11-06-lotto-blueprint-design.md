# 로또 6/45 개인 서비스 청사진

작성일: 2026-11-06

표시 규칙: **[요청]** 사용자가 정한 것 / **[판단]** 작성자가 정한 기본값(반대하면 바꿈)

## 1. 목적

혼자 쓰는 로또 도우미다. 역대 데이터를 보고, 매일 오후 5시에 통계 기반 추천 5줄을 텔레그램으로 받고, 추첨이 끝나면 그 주 추천이 어땠는지 확인한다. 어떤 전략이 무작위보다 나았는지도 숫자로 확인한다.

## 2. 목표 · 비목표 · 실패 조건

### 목표 [요청]
1. 역대 당첨번호 조회
2. 회차별 1~5등 당첨자 수와 지역 조회 (지역은 공개 범위까지, 3장 참고)
3. 매일 추천 5줄 생성과 근거 표시
4. 추첨 후 그 주 추천과 당첨번호 비교
5. 매일 17:00 텔레그램 추천 알림
6. 추첨 종료 텔레그램 알림
7. 추가 기능 5종: 인기 조합 피하기, 전략별 성적표, 과거 회차 시뮬레이션, 5줄 간 중복 최소화, 고정·제외 번호

### 비목표 [판단]
- 다중 사용자, 회원가입, 공개 서비스, 수익화
- 복권 구매 자동화, 실제 구매 내역 관리
- 텔레그램에서 명령을 받는 양방향 봇 (보내기 전용)
- 로또 6/45 외 다른 복권

### 실패 조건 (동작해도 실패로 본다)
- 추천을 "당첨 확률을 높인다"거나 "이번에 나올 번호"처럼 표현한다. 모든 조합의 1등 확률은 1/8,145,060로 같다.
- 추첨 후 지난 추천이 바뀐다. 비교와 성적표를 믿을 수 없게 된다.
- 시뮬레이션이 해당 회차 이후 데이터를 사용한다(미래 정보 누수).
- 데이터가 수집되지 않았는데 "추첨 종료"나 "낙첨"을 알린다.

## 3. 데이터 출처 (2026-11-06 실제 호출로 확인)

동행복권의 공개 API 문서는 찾지 못했다. 아래는 공식 사이트 화면이 내부적으로 쓰는 경로라서 **예고 없이 바뀔 수 있다.** 옛 경로 `common.do?method=getLottoNumber`는 홈으로 리다이렉트되어 더 이상 쓸 수 없다.

기준 URL: `https://www.dhlottery.co.kr`

| 용도 | 경로 | 확인한 내용 |
|---|---|---|
| 회차 목록 | `GET /lt645/selectLtEpsdInfo.do` | `data.list[]`: `ltEpsd`, `ltRflYmd`, `ltEpsdBgngYmd`, `ltEpsdEndYmd`. 1~1248회 전체 반환 |
| 회차 상세 | `GET /lt645/selectPstLt645InfoNew.do?srchDir=center&srchLtEpsd={n}` | 한 번에 10개 회차. `tm1WnNo`~`tm6WnNo`, `bnsWnNo`, `ltRflYmd`, `rnk1WnNope`~`rnk5WnNope`(인원), `rnk1WnAmt`~`rnk5WnAmt`(1인당 금액) |
| 당첨 판매점 | `GET /wnprchsplcsrch/selectLtWnShp.do?srchWnShpRnk=all&srchLtEpsd={n}&srchShpLctn=` | `region`, `shpNm`, `shpAddr`, `atmtPsvYnTxt`(자동/수동), `wnShpRnk`, `shpLat`, `shpLot`, `status` |

확인한 제약:
- **지역 데이터는 1·2등만 제공된다.** 3~5등은 인원과 금액만 있다. 화면 탭도 1·2등뿐이고, `srchWnShpRnk=3`을 보내면 필터 없이 전체(1·2등)를 돌려준다. 그래서 응답의 `wnShpRnk`로 등수를 판단한다.
- **오래된 회차는 판매점이 비어 있다.** 1회는 0건, 300회는 1등 12건이다. 경계 회차는 확인하지 않았고, 빈 결과는 화면에 "지역 정보 없음"으로 보여준다.
- 일부 초기 회차는 `rnk*SumWnAmt`, `winType*`가 0이다. 이 값들은 쓰지 않는다.
- `region`에 "전남광주" 같은 값이 온다. 행정구역이 바뀔 수 있으므로 enum 없이 문자열로 저장한다.
- 판매점 건수와 2등 인원이 1:1로 맞는지는 확인하지 않았다. 화면에 "당첨자 지역"이 아니라 "당첨 판매점 지역"으로 쓴다. 온라인 판매는 사이트가 지역 "서울", 주소 "동행복권(dhlottery.co.kr)"로 주며 지역 "인터넷"인 행은 없다. DB는 원본을 두고, API가 이 행을 지역 "온라인"으로 노출하며 `region` 필터도 같은 값을 쓴다(`region=온라인`은 이 행만, `region=서울`은 제외). 화면은 "온라인"을 별도 지역 묶음으로 보인다.

수집 원칙 [판단]:
- 요청 사이 최소 2초 간격, 초기 적재 후에는 새 회차만 요청한다. 500ms 간격으로 전량 적재하던 중 약 1,400회 요청 뒤 사이트가 약 1시간 응답하지 않았다(원인이 차단인지는 확인하지 못했다).
- 조회 화면은 항상 자체 DB를 읽고, 사용자 요청이 동행복권으로 바로 나가지 않는다.
- 이용약관은 확인하지 못했다. 개인 용도와 낮은 빈도를 전제로 하며, 공개 서비스로 바꾸면 다시 검토한다.
- 파서 테스트에 실제 응답 샘플을 픽스처로 저장한다. 형식이 바뀌면 조용히 잘못된 값을 넣지 말고 수집을 실패시켜 알림을 보낸다.

## 4. 동작 규칙

### 회차와 주간 경계
- 사이트의 판매 기간(`ltEpsdBgngYmd`~`ltEpsdEndYmd`)이 일요일~토요일이다(1248회: 10/25~10/31). 이 기준을 그대로 쓴다.
- 일~토 추천은 그 주 토요일 회차에 속한다. 토요일 17:00 추천은 판매 마감 전이므로 해당 회차에 포함되고, 한 회차는 최대 7일 × 5줄 = 35줄이다. [판단]
- 추천 생성 시 회차 번호는 `최신 저장 회차 + (대상 토요일 − 최신 회차 추첨일) / 7`로 계산한다. 직전 수집이 실패해도 회차가 어긋나지 않게 하기 위해서다. [판단]
- 모든 시각 계산은 `Asia/Seoul`로 한다.

### 추천 생성
- 매일 17:00에 생성 후 바로 발송한다. [요청]
- 날짜별 1벌만 만들고 수정하지 않는다. 날짜+전략 유니크 제약으로 중복을 막는다. [판단]
- 서버가 17:00에 꺼져 있었다면 기동 시 그날 추천이 없고 17:00이 지났을 때만 생성·발송한다. 지난 날짜는 소급 생성하지 않는다. [판단]
- 토요일 20:00(판매 마감) 이후에는 보충 생성하지 않는다. 마감된 회차의 추천이 생기거나 당첨번호가 통계에 섞이는 일을 막기 위해서다. [판단]
- 통계는 생성 시점까지 수집된 회차만 쓴다. 입력 회차 범위, 전략별 근거 수치, 적용된 고정·제외 번호, 제약 완화 여부를 추천과 함께 저장한다. 난수 시드는 저장하지 않는다. [판단]

### 전략 5종 (한 줄에 한 전략) [판단]
| 전략 | 번호 가중치 | 근거 표시 예 |
|---|---|---|
| `RECENT_HOT` | 최근 50회 출현 빈도 | "번호 3: 최근 50회 중 11회 출현" |
| `LONG_COLD` | 마지막 출현 후 지난 회차 수 | "번호 39: 23회째 미출현" |
| `ALL_TIME` | 전체 회차 출현 빈도 | "번호 3: 전체 1248회 중 190회 출현" |
| `PAIR` | 함께 자주 나온 번호 쌍 빈도 | "12·34 쌍이 N회 함께 출현" |
| `BALANCED` | 균등 가중, 대신 홀짝·저고(1~22/23~45)·합계를 과거 분포 중앙 50% 안으로 제한 | "홀3:짝3, 합계 137, 과거 분포 중앙 구간" |

- 근거는 어떤 번호의 수치인지 문구에 드러낸다. 횟수는 번호와 헷갈리지 않게 "번" 대신 "회"로 적는다.

- 가중 무작위 추출이다. 데이터는 일주일 동안 안 바뀌므로 고정 선택이면 매일 같은 번호가 나온다. 난수는 주입된 `Random`(운영 `SecureRandom`, 테스트 시드 고정)을 쓴다.
- 화면과 메시지에 "실제 당첨 확률과 무관합니다."를 표시한다. (2026-11-09 사용자 결정으로 "번호 선택 방식 설명이며 당첨 확률과 무관함"에서 변경)

### 공통 제약 (적용 순서)
1. **고정·제외 번호** [요청]: 사용자 설정을 추천 5줄과 대조군 5줄 모두에 적용한다. 변경은 다음 생성부터 반영한다.
   - 기존 에러 코드 `DRAW_NUMBER_OUT_OF_RANGE`, `DRAW_FIXED_EXCLUDED_OVERLAP`, `DRAW_NOT_ENOUGH_CANDIDATES`를 재사용한다.
   - 고정 번호 상한은 5개다. 6개면 5줄이 모두 같아진다. [판단, 기존 도메인 규칙은 ≤6]
2. **인기 조합 피하기** [요청]: 다음 조합을 다시 뽑는다. 당첨 확률은 그대로이고, 1등 시 나눠 가질 사람이 줄 가능성만 노린다. [판단]
   - 전부 31 이하(생일 번호)
   - 4개 이상 연속 번호
   - 전체 등차수열
   - 과거 1등 조합과 동일
3. **줄 간 중복 최소화** [요청]: 고정 번호를 뺀 겹침이 다른 줄과 2개 이하가 되게 한다. [판단]

제약을 지키지 못하면 재추출 최대 1,000회 후 3 → 2 순서로 완화하고, 완화 사실을 근거에 표시한다. 고정·제외 규칙은 완화하지 않는다. [판단]

### 대조군 [판단]
매일 균등 무작위 5줄을 함께 저장하되 추천 화면과 알림에는 보내지 않는다. 성적표 비교에만 쓴다. 추천 5줄을 통계 전략으로 채워 달라는 요청을 지키기 위해 따로 둔다. 고정·제외 번호는 적용하고, 인기 조합 필터와 줄 간 중복 제약은 적용하지 않는다.

### 수집과 추첨 종료 알림 [판단]
- 토요일 20:40부터 5분마다 새 회차를 확인한다(방송 시각이 아니라 데이터 기준).
- 토요일 자정 이후에는 1시간마다 확인한다. 일요일 12:00까지 없으면 "수집 실패" 알림을 1회 보내고, 수집될 때까지 1시간 간격으로 계속 확인한다. 없는 결과를 낙첨으로 처리하지 않는다.
- 서버 기동 시 빠진 회차를 모두 수집한다. 늦게 수집된 회차도 비교를 계산한다.
- 번호가 수집되면 비교를 계산하고 회차별 종료 알림 1회를 보낸다. 늦게 수집됐으면 그 사실을 함께 적는다. 내용: 회차, 당첨번호, 줄별 최고 등수와 등수별 줄 수, 가상 당첨금 합계.
- 판매점은 비동기로 공개될 수 있으므로 비어 있으면 7일 동안 매일 재시도한다.

### 비교와 성적표
- 등수는 도메인 규칙을 따른다: 1등 6개 / 2등 5개+보너스 / 3등 5개 / 4등 4개 / 5등 3개 / 그 외 낙첨.
- 추천 줄은 본번호 6개만 있고 `bonus`가 없다.
- 가상 당첨금은 회차의 1인당 금액으로 계산하고 "구매했다고 가정"으로 표시한다. 줄당 1,000원 가정의 가상 수익도 같이 보여준다. [판단]
- **성적표** [요청]: 전략별 + 대조군의 누적 줄 수, 평균 일치 개수, 등수별 건수, 5등 이상 비율을 보여준다. 이론값(5등 이상 약 2.4%)도 함께 보여준다. 고정·제외 번호가 적용된 줄이 있으면 전략과 대조군 비교에는 포함하되, 이론값 비교에서는 설정 없는 줄만 사용하고 그 줄 수를 표시한다. [판단]
- 표본이 작을 때는 "아직 차이를 판단하기 이르다"고 표시한다.

### 과거 회차 시뮬레이션 [요청]
- 각 회차 r에 대해 r 이전 데이터만으로 전략을 실행한다. 통계가 안정되도록 101회부터 시작한다. [판단]
- 전략별로 회차당 고정 시드로 N회 추출한다(기본 200). 대조군 포함. [판단]
- 결과: 전략별 평균 일치 개수, 등수 분포, 5등 이상 비율과 회차 단위로 계산한(같은 회차의 줄은 함께 채점되므로) 95% 신뢰구간, 대조군·이론값 비교. 구간이 겹치면 "유의한 차이 없음"으로 표시한다. [판단] (2026-11-09 변경)
- 고정·제외 번호, 인기 조합 필터, 줄 간 중복 제약은 모두 적용하지 않는다. 각 전략의 번호 추출 규칙만 평가하며(`BALANCED`의 범위 제한은 전략의 일부이므로 포함), 화면에 이 범위를 명시한다. [판단]
- 새 회차 수집 후 자동 재계산하고 마지막 결과만 저장한다. 요청 시점에 계산하지 않는다. [판단]

### 텔레그램 [요청 + 판단]
- Bot API `sendMessage`, 설정은 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` 환경변수만 사용한다. `.env.example`에 키 이름을 추가한다.
- 발송 전 알림 기록을 저장한다(종류, 날짜/회차, 상태). 같은 알림 중복 전송을 막고 실패 시 3회 재시도한다.
- 번호 생성이 끝났는데 발송이 실패해도 추천은 유지한다. 화면에 발송 실패를 표시한다.

기존 규칙(`.claude/rules/api.md`, `web.md`, `testing.md`, `lotto-domain.md`, `api-conventions` 스킬)을 그대로 따른다.

### API 패키지 (`com.lotterypicker.*`)
| 패키지 | 책임 |

| `round` | 회차, 번호, 등수별 인원/금액, 판매점 저장·조회 |
| `collector` | 동행복권 클라이언트와 초기 적재, 스케줄 수집 |
| `recommendation` | 번호 값 객체 `LottoNumbers`, 전략, 제약, 일일 생성, 설정 |
| `result` | 추천과 당첨번호 비교, 성적표 |
| `simulation` | 과거 회차 시뮬레이션 |
| `notification` | 텔레그램 발송과 발송 기록 |
| `auth` | OTP 로그인, 세션, 잠금 (6장) |

- 번호 생성은 `apps/api` `recommendation` 패키지 한 곳에만 둔다. 프론트는 호출·표시만 한다.
- `lotto-domain.md`의 `LottoDrawService`와 수동 추첨 옵션은 아직 코드가 없다. 수동 추첨 API는 만들지 않고, 규칙 문서를 추천 기준으로 갱신한다. [판단]
- 추천 기록은 수정 경로를 두지 않는다.
- 스케줄은 Spring `@Scheduled(zone = "Asia/Seoul")`, 외부 호출은 Spring의 HTTP 클라이언트를 쓴다.
- 운영 DB는 기존 프로파일대로 MySQL(`ddl-auto: validate`)이다. 스키마 관리 도구는 아직 없으므로 Flyway를 도입한다. [판단]

### API 엔드포인트 (`/api/v1`) [판단]
| 메서드/경로 | 내용 |
|---|---|
| `GET /rounds?page&size` | 회차 목록(최신순) |
| `GET /rounds/{round}` | 번호, 보너스, 등수별 인원/금액 |
| `GET /rounds/{round}/winning-stores?rank&region` | 1·2등 판매점 |
| `GET /rounds/{round}/results` | 그 회차 추천 비교 결과 |
| `GET /recommendations?date` | 날짜별 추천과 근거 (기본: 오늘) |
| `GET /strategy-performances` | 전략 성적표 |
| `GET /simulations/latest` | 최신 시뮬레이션 결과 |
| `GET·PUT /recommendation-settings` | 고정·제외 번호 |

새 에러 코드는 `ErrorCode` enum에 `<DOMAIN>_<REASON>` 형식으로 추가한다.

### 웹 화면 (`apps/web`) [판단]
| 경로 | 내용 |
|---|---|
| `/` | 오늘 추천 5줄과 근거, 최신 회차 요약 |
| `/rounds` | 역대 당첨번호 목록 |
| `/rounds/[round]` | 등수별 인원·금액, 1·2등 지역, 그 회차 추천 비교 |
| `/performance` | 전략 성적표 + 시뮬레이션 결과 |
| `/settings` | 고정·제외 번호 |

시각 디자인은 빌더 재량이다. 사용자 전용 도구답게 숫자가 잘 읽히는 모바일 우선 화면으로 만든다. 텔레그램 알림을 받고 폰에서 열어볼 가능성이 높기 때문이다.

## 6. 운영

### 실행 위치 [요청]
- 집에 있는 상시 서버에서 웹, API, MySQL을 함께 실행한다.
- 설치 방식과 재부팅 후 자동 시작은 서버 사양을 확인한 뒤 배포 태스크에서 정한다. [판단]
- 배포 전에 서버에서 3장의 동행복권 경로에 접속되는지 확인한다.
- 집 밖에서 쓰려면 HTTPS 경로가 필요하다. 서버(Synology NAS)의 DSM 역방향 프록시가 HTTPS(Let's Encrypt)를 받아 `127.0.0.1`에만 열린 웹으로 넘긴다. 공유기는 80·443만 연다. [판단] (2026-11-09 변경)

### 접근 제어: 개인 OTP [요청]
- 사용자는 한 명이다. ID·비밀번호 없이 OTP 앱의 6자리 코드(TOTP, RFC 6238)로 로그인한다.
- 비밀키는 환경변수 `TOTP_SECRET`으로만 관리하고 `.env.example`에는 키 이름만 적는다. 첫 등록은 서버에서 일회성 명령으로 QR을 출력해 진행한다. [판단]

구현 기준 [판단]:
- 인증은 `apps/api` `auth` 패키지 한 곳에서 처리한다. `POST /api/v1/sessions`(로그인), `DELETE /api/v1/sessions`(로그아웃)를 둔다.
- 건강 확인과 로그인 외의 모든 API는 세션이 없으면 401을 반환한다.
- 세션은 `HttpOnly`, `Secure`, `SameSite=Strict` 쿠키이고 유효 기간은 30일이다. DB에는 토큰 해시만 저장해 재시작 후에도 유지되게 한다.
- 추측 공격을 막기 위해 연속 5회 실패 시 15분 동안 로그인을 잠근다. 잠금 상태는 DB에 저장한다. 이미 사용한 코드는 다시 받지 않는다. 시계 오차는 앞뒤 1구간(30초)까지 허용한다.
- 브라우저는 웹과 같은 주소의 `/api/*`로 호출하고 Next.js가 API로 전달한다. API는 외부에 직접 열지 않는다.
- 이 변경에 맞춰 `.claude/rules/web.md`의 `NEXT_PUBLIC_API_URL` 호출 규칙과 `lib/api.ts`, CORS 설정을 고친다.
- 새 에러 코드: `AUTH_REQUIRED`(401), `AUTH_INVALID_CODE`(400), `AUTH_LOCKED`(429). `api-conventions`의 상태 코드 목록에 401, 429를 추가한다.

분실 대응: 휴대폰을 잃으면 서버에서 `TOTP_SECRET`을 새로 만들고 재시작한 뒤 다시 등록한다. 기존 세션은 이때 모두 폐기한다. 복구 코드는 만들지 않는다. [판단]
