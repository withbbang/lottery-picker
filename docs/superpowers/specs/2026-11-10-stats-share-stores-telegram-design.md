# 번호 통계 · 추천 공유 · 판매점 지역/지도 · 텔레그램 명령어

작성일: 2026-11-10

표시 규칙: **[요청]** 사용자가 정한 것 / **[판단]** 작성자가 정한 기본값(반대하면 바꿈)

네 기능은 서로 독립이고 각각 별도 피처 브랜치(`dev`에서 분기)로 진행한다. 구현 순서 [판단]: 1 → 2 → 3 → 4. 4(텔레그램)의 `/stats`가 1의 통계 API를 재사용하므로 마지막에 둔다.

공통 원칙(기존과 동일):
- 숫자 계산·집계는 `apps/api`에서만. 웹·텔레그램은 받은 값을 보여 주기만 한다.
- 응답 포맷·URL·에러 코드는 `api-conventions` 스킬을 따른다.
- "당첨 확률을 높인다" 류의 표현은 쓰지 않는다.

## 1. 번호 통계 화면

### 왜 [요청]
추천을 받은 뒤 근거("번호 7: 최근 50회 중 4회 출현")가 45개 번호 전체와 비교해 정말 두드러지는지 확인하려고. 심심풀이 둘러보기 용도가 아니다.

### 현재 상태
- 통계는 엔진 내부 `NumberStatistics`(`recommendation/engine`)에만 있고 화면이 없다.
- 근거 문구는 `WeightedSampler.Sample.evidence`가 만든다: `RECENT_HOT` "최근 50회 중 N회 출현"(`RecentHotStrategy.WINDOW = 50`), `LONG_COLD` "N회째 미출현", `ALL_TIME` "전체 T회 중 N회 출현". 각 줄당 가중치 상위 최대 2개 번호.
- 추천 행마다 `history_from_round`, `history_to_round`(계산에 쓴 회차 범위)가 저장돼 있다.

### 동작
- [요청] 지표 탭 3개: **최근 50회 출현 / 미출현 회차 / 전체 출현**. 각각 `RECENT_HOT`, `LONG_COLD`, `ALL_TIME` 근거에 대응한다.
- [요청] `PAIR`(번호 쌍)과 `BALANCED`(홀짝·합계) 근거는 이번 범위 밖.
- [요청] 통계는 **그 추천을 만든 시점의 회차 범위**로 계산한다. 근거 문구의 숫자와 화면 숫자가 항상 일치해야 한다. 새 회차가 수집돼도 그 추천의 통계는 바뀌지 않는다.
- [판단] API가 추천 날짜(또는 그 날짜의 회차 범위)를 받아 45개 번호의 세 지표 값과 순위를 돌려준다. 계산은 `NumberStatistics`를 그대로 쓴다(근거와 같은 계산식 보장). 윈도 50은 `RecentHotStrategy`와 같은 상수를 공유해 어긋나지 않게 한다. URL·파라미터 모양은 빌더가 `api-conventions`에 맞춰 정한다.
- 한 날짜의 추천 줄들은 같은 회차 범위를 쓴다(공통 빌더 사용으로 확인됨).
- [판단] 저장된 `history_from_round`~`history_to_round` 범위로 다시 계산한다. 통계 스냅샷은 저장하지 않는다. 수집된 회차의 당첨 번호는 바뀌지 않고, 수집은 회차를 빠짐없이 순서대로 쌓으므로 같은 범위면 같은 값이 나온다는 전제다. 이 전제를 테스트로 고정한다(저장된 근거 문구의 숫자 = 재계산 값).
- [판단] 순위는 공동 순위("공동 4위"). 미출현 회차는 값이 클수록 위.

### 화면 [요청: B안 순위 막대]
- 선택한 지표로 45개 번호를 줄 세운 가로 막대 목록. 각 행: 번호(공), 막대, 값, 강조 번호에는 순위.
- 상단에 기준 안내 한 줄 [판단]: "M월 D일 추천 기준 · 1~N회".
- [판단] 진입은 링크로만. 하단 탭바에 새 칸을 만들지 않는다(기존 "통계" 탭은 성적표다). 페이지 이름은 "번호 통계".
- [판단] 진입 경로:
  - 오늘 추천 카드의 근거 펼침 영역에 "통계에서 보기" 링크. `RECENT_HOT`/`LONG_COLD`/`ALL_TIME` 줄에만 둔다.
  - 지난 추천 기록 화면(`RecommendationHistory.tsx`)에도 같은 링크(그 날짜 기준). **지금 기록 화면은 근거를 그리지 않으므로**, `RecommendationCard`의 근거 펼침 부분을 공용 컴포넌트로 빼서 기록 화면에도 붙인다 [판단]. 응답에는 이미 `evidence`가 있다.
- [판단] 강조: 링크를 누른 줄의 **근거 번호**(최대 2개)만 주황 계열로 강조하고, 그 전략에 맞는 탭이 먼저 열린다. 웹은 문구를 파싱하지 않고 API의 구조화된 값으로 받는다.
- [판단] 근거 번호 저장: 지금 근거 번호(`Ingredient`)는 생성 중 메모리에만 있고 DB와 응답에는 문구만 있다. 그래서
  - 새 마이그레이션(V9)으로 줄마다 근거 번호를 저장하는 컬럼을 추가하고, 앞으로 생성하는 추천은 엔진의 구조화된 값을 그대로 저장한다.
  - 이미 쌓인 추천은 **서버에서 한 번만** 저장된 근거 문구의 `"번호 N: "` 접두어를 읽어 채운다(우리 코드가 만든 고정 형식이라 안전). 웹 파싱 금지 원칙은 유지된다. 채우는 방식(Flyway Java 마이그레이션, 기동 시 1회 작업 등)은 빌더 재량.
  - 추천/기록 응답에 줄별 근거 번호 필드를 추가한다.
- 대조군 줄은 화면에 나오지 않으므로 링크도 없다.

### 비목표
- 최신 회차 기준 "현재" 통계 보기, 번호 쌍·균형 시각화, 차트 라이브러리 도입.

## 2. 추천 줄 복사 · 공유

### 왜 [요청]
판매점에서 번호를 보고 마킹하는 용도와, 카톡 등으로 남에게 보내는 용도 **둘 다**.

### 동작 [판단, 사용자 미반대]
- **줄마다 복사 버튼**: 그 줄 번호 6개를 두 자리 공백 구분으로 복사(`03 07 12 27 33 40`).
- **전체 공유 버튼**: `navigator.share`가 있으면 기기 공유 시트, 없으면(PC 등) 클립보드 복사로 대체하고 "복사됨" 피드백.
- 공유 텍스트: 첫 줄에 날짜와 회차, 이어서 화면에 보이는 줄들(전략 5줄 + 근거 조합 줄)을 화면과 같은 줄 이름과 함께 한 줄씩. 근거 문구는 넣지 않는다. 대조군은 넣지 않는다.
- 판매점 표시용 별도 화면은 만들지 않는다(기존 카드의 공이 충분히 크다).
- 지난 추천 기록 화면에도 같은 버튼을 둘지는 빌더 재량(넣는다면 같은 컴포넌트 재사용).
- 순수 웹 기능. API 변경 없음.

## 3. 당첨 판매점 지역 통계 · 지도

### 왜 [요청]
"우리 동네에서 1등이 몇 번 나왔나"와 "전국에서 어디가 많이 나오나" **둘 다** 궁금하다.

### 현재 상태
- `winning_store`: 회차, 등수(`win_rank` 1·2), `region`(시·도), `name`, `address`(대부분 도로명 주소), `purchase_type`(자동/수동), `latitude`, `longitude`, `status`.
- 화면은 회차 상세에서 그 회차 판매점만 보인다.
- 온라인 판매는 원본이 지역 "서울", 주소 "동행복권(dhlottery.co.kr)"이며 API가 지역 "온라인"으로 노출한다(기존 규칙). 집계에서도 "온라인"으로 따로 묶는다.
- 오래된 회차는 판매점 데이터가 없다(1회 0건, 300회 1등 12건).

### 동작
- [판단] **전국**: 시·도별 당첨 판매점 건수 순위. 1등/2등 전환(기본 1등). "온라인"은 별도 항목.
- [판단] **시·군·구**: 시·도를 고르면 그 안의 시·군·구별 순위. 시·군·구는 주소 앞부분에서 뽑는다(예: `서울 중랑구 …` → 중랑구). 세종처럼 시·군·구가 없는 곳, 경기 `수원시 장안구`처럼 두 단계인 곳 등 예외 처리는 빌더 재량이되 규칙을 테스트로 고정한다. 추출은 API에서.
- [요청] **동 단위 목록은 만들지 않는다.** 도로명 주소에 동이 없는 경우가 많아 정확하지 않다. 대신 **지도**로 해결한다.
- [요청] **지도**: 시·군·구(또는 시·도)를 고르면 지도가 그 영역으로 이동·확대되고, 1등(전환 시 2등)이 나온 판매점을 핀으로 보인다. 같은 판매점의 여러 번 당첨은 핀 하나에 횟수 표시.
- [판단] **판매점 순위**: 당첨이 여러 번 나온 판매점 목록(선택한 지역 범위 안). 같은 판매점 판정은 이름+주소 기준(판매점 고유 ID가 없음). 폐업 등 `status`는 원본대로 표시만.
- [판단] 집계 기간을 화면에 명시: "판매점 정보가 있는 N회~M회 기준".
- [판단] 안내 한 줄: "판매점이 많은 지역일수록 당첨도 많이 나옵니다." (지역 순위가 운을 뜻하지 않음을 알림)
- 좌표가 없는 행과 온라인은 지도에서 빠지고 목록에만 나온다.

### 지도 기술 [판단, 사용자 미반대]
- OpenStreetMap 타일 + Leaflet(React 래퍼 포함 여부는 빌더 재량). API 키 불필요. OSM 저작권 표기 필수.
- Leaflet은 SSR에서 `window`를 쓰므로 클라이언트 전용으로 불러온다. 새 의존성은 `node_modules`의 실제 타입을 읽고 쓴다.
- 카카오맵은 쓰지 않는다(키 발급·도메인 등록 부담). 나중에 바꿀 수 있게 지도 부분을 한 컴포넌트에 가둔다.

### 화면 위치 [판단]
- "회차" 탭 안의 새 페이지(예: `/rounds/stores`)로 두고 회차 목록 상단에서 링크. 하단 탭바는 그대로.

### 비목표
- 동 단위 목록, 외부 지오코딩 API, 인구·판매점 수 대비 보정 통계, 내 위치 기반 "가까운 명당".

## 4. 텔레그램 봇 명령어

### 왜 [요청]
웹사이트 기능을 한눈에 찾아보기 번거로울 때, 텔레그램에서 특정 기능을 바로 확인하려고.

### 현재 상태
- `TelegramClient`는 보내기 전용(`send(String)` → Bot API `sendMessage`, `parse_mode=HTML`), 설정 `app.telegram.bot-token`, `app.telegram.chat-id`.
- 스케줄러 스레드 풀은 2개, RestClient read-timeout은 30초다. 롱 폴링은 전용 스레드와 별도 타임아웃(폴링 대기시간보다 길게)으로 분리해 기존 스케줄을 막지 않게 한다 [판단].
- 메시지 문구는 `MessageFormatter`, 예시는 `docs/telegram-messages.md`.

### 명령어 [요청]
| 명령 | 내용 |
|---|---|
| `/today` | 오늘 추천(없으면 웹과 같은 규칙으로 직전 추천) — 전략 5줄 + 근거 조합 줄 |
| `/result` | 최근 채점된 회차의 당첨 번호와 내 추천 채점 결과 |
| `/performance` | 전략별 성적표 요약 |
| `/round N` | N회 당첨 번호, 등수별 당첨금, 1등 판매점 지역 |
| `/stats` | 번호 통계 요약: 탭마다 상위 5개 번호 |
| `/settings` | 현재 고정·제외 번호 **보기만** |
| `/help` | 명령 목록 |

- [판단] `/stats` 기준은 **가장 최근 추천의 회차 범위**(1과 같은 원칙, 근거와 숫자 일치).
- [판단] 봇 시작 시 `setMyCommands`로 `/` 메뉴 등록.
- [판단] 숫자는 웹과 같은 서비스 계층을 호출해 만든다. 텔레그램 전용 계산 로직을 두지 않는다.
- [판단] 알 수 없는 명령·잘못된 인자(`/round abc`, 없는 회차)는 짧은 안내와 `/help` 유도. 데이터가 아직 없으면(추천 전, 채점 전) 그 사실을 그대로 말한다.

### 보안 [판단, 사용자 미반대]
- 설정된 `chat-id`에서 온 메시지에만 응답한다. 그 외는 무시(응답하지 않음, 로그만).
- 설정 변경은 텔레그램에서 하지 않는다(웹은 TOTP로 보호되는데 우회 경로가 생기므로).
- 토큰이 로그·예외 메시지에 새지 않게 기존 `TelegramClient` 원칙 유지.

### 수신 방식 [판단, 사용자 미반대]
- **롱 폴링**(`getUpdates`)으로 받는다. NAS를 외부에 새로 열지 않는다. 웹훅은 쓰지 않는다.
- 봇 토큰이 없으면(`isConfigured()` false) 폴링을 시작하지 않는다. 로컬·테스트에서 돌지 않게 한다.
- 처리한 업데이트는 `offset`으로 확인 처리한다. 재시작 직후 밀린 오래된 명령(예: 수 분 이상 지난 것)에 답할지는 빌더 재량이되, 같은 명령에 두 번 답하지 않게 한다.
- 텔레그램 장애·타임아웃 시 백오프 후 재시도. 폴링 실패가 추천 생성·알림 발송 스케줄에 영향을 주지 않게 분리한다.

### 비목표
- 웹훅, 설정 변경 명령, 여러 사용자 지원, 인라인 버튼/키보드.
